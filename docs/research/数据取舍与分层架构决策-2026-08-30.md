# 大规模司法数据取舍决策 —— 从「全量内置」到「分层电子地图」（2026-08-30）

> 业主之问：大规模数据应如何取舍？还是能全盘接受？原期望是把所有案例内置并持续更新，做成「电子图书馆 / 电子地图」式配置，让用户快速找到案例与结果、获得参考方向；定位是有温度的普法 + 为法律灰色地带案件提供判罚资料参考，辅助更好的庭审判罚（真实求助仍需专业律师）。
> 本文以官方制度与既有调研（`庭审判罚刑侦案件数据源调研-2026-08-30.md`）为依据给出决策，并落地到产品。

## 一、决策结论（先答问题）

**不全盘接受，也不靠砍功能妥协愿景——把「全量内置」重构为「分层电子地图」三层架构：**

| 层 | 类比地图 | 内容 | 规模 | 更新 |
|---|---|---|---|---|
| **L1 精选层（内置底图）** | 离线底图 | 两高指导性/典型案例 + 人民法院案例库参考案例，全结构化 | 约 6–8 千件（≈20MB 级） | 官方批次=版本发布 |
| **L2 统计层（聚合路况）** | 路况聚合 | CAIL 268 万刑事文书 → 脱敏 → 聚合为「罪名×法条×刑期分布」统计 | 聚合表，不存个案 | 数据集版本 |
| **L3 联邦层（实时瓦片）** | 瓦片流式加载 | CourtListener / CAP / EUR-Lex / legislation.gov.uk 开放 API | 检索时调用、按需缓存 | API 实时 |

电子地图从来不是「把整个地球存进手机」——底图内置、路况流式、瓦片按需。司法数据同理：**「全」通过联邦实现，「准」通过内置实现。**

## 二、为什么不能全盘接受（三条硬边界）

1. **合法性边界**：裁判文书网上网文书已从 2020 年 1,920 万件收缩至 2022 年 1,040 万件且无开放批量授权（最高法答记者问）；检察案例库为内部系统。全量抓取直接违反本项目红线第 7 条（三重授权原则）。CAIL 268 万份可用，但含个人信息：**全量内置 = 无限的 PIPL 删除义务敞口**；聚合统计则使敞口归零。
2. **工程边界**：GB 级存储与索引维护成本高，但这不是主要矛盾——
3. **效用边界（最关键）**：普通用户在 268 万份原始文书里检索，等于在无人整理的仓库里找东西。司法数据的价值不在「全」而在「**结构与顺位**」。连法官都不用全量：官方类案检索制度正是为解决「全而无序」设计的（见 §三）。

## 三、制度锚点：官方已给出取舍标准（法发〔2020〕24号）

《最高人民法院关于统一法律适用加强类案检索的指导意见（试行）》（2020-07-27 发布，[官方原文 court.gov.cn/fabu/xiangqing/243981.html](https://www.court.gov.cn/fabu/xiangqing/243981.html)；[人民网刊发全文](http://legal.people.com.cn/n1/2020/0727/c42510-31799111.html)）：

- **第二条 · 应当检索的情形**之一：「**缺乏明确裁判规则或者尚未形成统一裁判规则**」——这正是「法律灰色地带」的官方表述。**本项目的灰色地带定位与官方制度的自身需求同构**，不是我们自创的场景。
- **第四条 · 检索顺位**（取舍原则的直接依据）：
  ① 最高法**指导性案例** → ② 最高法**典型案例**及生效裁判 → ③ 本省高院**参考性案例**及生效裁判 → ④ 上一级法院及本院生效裁判；除指导性案例外优先**近三年**。
- **第九条 · 结果运用**：指导性案例可作**裁判理由引述**（不得作裁判依据）；其他类案作**参考**；**当事人、辩护人、诉讼代理人提交指导性案例或其他类案支持主张的，法官应当在裁判文书说理中回应**。
- 配套：《统一法律适用工作实施办法》（法〔2021〕289 号）要求承办法官**制作类案检索报告**随案归档。

→ **取舍原则 = 官方顺位即分层**：顺位越靠前越深度内置（L1），越靠后越联邦化（L3）；「辅助庭审」的合法角色 = 为法官/律师/当事人生产**制度内本来就需要的类案检索材料**，而非预测裁判。

## 四、三层架构细则

### L1 精选层（内置底图）——「电子图书馆」本体
- 来源与路径沿用调研 P0/P1：两高官方发布文本（进行中，现有 5 件样本）+ 人民法院案例库 5,040 件（2025-07 官方口径：刑事 1,912 / 民事 2,159，[上线发布](https://www.court.gov.cn/zixun/xiangqing/426222.html)）按篇录入核对。
- 每件结构化字段：事实 / 争议焦点 / 裁判要旨 / 引用法条（版本化）/ **类案检索顺位徽章** / 官方来源 URL。
- 规模测算：全部录入 ≈ 6–8 千件 × ~3KB ≈ 20MB——**完全可内置，且这就是「把所有值得内置的案例内置」**（顺位①②的全部 + 顺位③的精华）。
- 公众层增强：白话解说 + 普法贴士（温度组件复用），专业层保留原文与引用链。

### L2 统计层（聚合路况）——灰色地带的「参考方向」
- CAIL 268 万份刑事文书（[thunlp/CAIL](https://github.com/thunlp/CAIL)）不存个案，脱敏后聚合成「罪名 × 法条 × 刑期区间」分布表。
- 服务方式：用户查询灰色地带问题时，呈现「公开数据集中该罪名量刑分布（统计口径 + 年份 + 数据来源）」——给方向、不下结论；正文使用 Legal Safety 句式（「公开数据中观察到……」「可能涉及……」）。
- 合规：不展示个体文书 → PIPL 个案敞口≈0；数据集版本与脱敏口径随统计披露。

### L3 联邦层（实时瓦片）——「全」的合规实现
- CourtListener（[API](https://www.courtlistener.com/)，数百万 opinions，3,359 辖区）、CAP（[case.law](https://case.law/) bulk）、EUR-Lex CELLAR、legislation.gov.uk（OGL v3.0）。
- 检索时调用、结果逐条带来源与许可、可按需缓存；**不承诺也不宣称全量镜像**（数据源页如实标注）。

### 持续更新机制（对齐「电子地图」运营感）
- L1：官方批次监更（新批次指导/典型/参考案例 → 人工核对 → 版本发布，类似地图季度更新）；
- L2：CAIL/数据集版本升级时重算聚合；
- L3：API 天然实时。

## 五、「辅助庭审」的角色边界（合规红线，写死）

| 可以做（制度内角色） | 不可以做 |
|---|---|
| 类案检索工具（按官方顺位排序呈现） | 预测/承诺裁判结果（红线词 gate 已拦截） |
| 生成类案检索报告式材料（对应法〔2021〕289 号检索报告制度） | 代替法官判断（最高法「AI 不得代替法官裁判」） |
| 为当事人/律师准备诉辩用的类案材料（第九条回应义务的输入） | 以律师名义执业 |
| 统计分布「参考方向」 | 确定性表述「法院会判……」 |

## 六、对原愿景的逐条回应

| 业主原期望 | 分层架构的回应 |
|---|---|
| 所有案例内置并持续更新 | L1 将全部高权威案例（顺位①②全集+③精华）内置并随官方批次更新；「全量亿级文书」即使合法也无效用，且与电子地图同构的方案（底图+瓦片）反而更快更准 |
| 电子图书馆 | L1 即图书馆核心馆藏（官方审定的书才上架） |
| 电子地图 | 三层=底图/路况/瓦片，架构同构 |
| 方便快捷找到案例与结果 | 按官方顺位排序的检索 > 全文堆砌；统计层给「结果参考方向」 |
| 仅作参考方向 | 第九条规则内置到 UI：指导性案例=「可作裁判理由引述」，其余=「参考」，永不显示为依据 |
| 有温度的普法 | L1 公众层（白话+12348/证据留存/诉讼时效温度组件） |
| 灰色地带判罚资料 | 第二条即官方触发情形；L2 统计分布 + L1 类案 + 法条库三路供给 |
| 辅助更好的庭审判罚 | 类案检索报告材料 = 制度内工具；三道 gate 确保不越界 |

## 七、落地映射（写入 v2 计划 M6）

- **M6-T2 改制**：「判例库接入」→「L1 案例库录入流水线（含 `tier` 顺位字段与徽章）」；
- **新增 M6-T7**：L2 CAIL 统计管道（下载→脱敏→聚合→统计卡组件）；
- **新增 M6-T8**：L3 CourtListener 联邦检索（只读 API，结果带来源缓存）；
- 前端即时落地：案例卡/详情显示**类案检索顺位徽章**（依据法发〔2020〕24号第四条），让「取舍标准」成为产品可见的秩序。
