## 二、方案评估：electron-updater + GitHub Releases 通道【中——待实施核验】

- electron-builder 长期提供 GitHub Releases 作为 update provider：构建时生成 `latest.yml`
  清单并随安装包上传；运行时 electron-updater 检查 `https://github.com/Rethymus/LegalHigh/releases/download/<tag>/latest.yml` 比对版本。
- **本轮核验尝试失败**：electron.build 文档站两次访问 404/ECONNRESET，GitHub raw 文档路径 404。
  上述通道描述来自长期社区共识记忆，**实施前必须以 electron-builder 仓库内文档核验当前配置键名**
  （26.x 大版本曾有 publish 配置迁移）。
- 平台差异（同上，待核验）：macOS 自动更新**强制要求签名**；Windows 未签名可更新但触发
  SmartScreen/发布者未知告警；Linux AppImage 未签名可更新。本项目 Windows 优先（目标用户）。

## 四、初步结论

1. **技术可行性与维护成本低**：electron-builder 原生通道，不需要自建更新服务器；静态资产走
   GitHub Releases 免费 CDN。
2. **签名是体验与合规的分水岭**（决策 16）：不签名=可用但有 OS 级告警（需 README 明示）；
   签名=证书采购（Windows EV 数千元/年量级 + Apple 开发者账号），并解锁 macOS 自动更新。
3. **顺序建议**：先做 PoC 步骤 1–2（不依赖证书）确认通道与告警形态 → 业主据实拍板决策 16 →
   签名路线再补 3 平台安装/卸载/升级验收（对应 v1.1.0-rc.1「未完成三平台签名安装验收」的既有声明）。
4. **当前不作任何自动更新承诺**：rc.1 无安装器，README 口径不变。
