# LegalHigh 决策清单 —— 待决策项分析（2026-08-30）

> 背景：查漏补缺四轮（`开发计划-v3-查漏补缺与打磨.md`）后，登记册上剩余事项中有一部分不是「执行任务」而是「需要拍板的选择」。本文逐项给出选项、利弊与推荐，供决策。
> 决策原则（从项目本质导出）：①可信与可溯源优先于功能先进性；②人机协同双轨优先于全自动；③宁缺毋假、诚实降级；④尊重「非必要不决策」授权——优先可逆、零外部承诺的动作，把大决策转化为「条件触发」。

## 决策项 1：v6 窄屏形态的完成路径（登记册 C4 剩余）

**现状**：窄屏基线已落地（抽屉侧栏+单列栅格，390×844 全路由可用）。完整 v3 形态（底部标签栏 / BottomSheet / 44pt 触摸目标 / safe-area / 大字模式）完整存在于 `src-legacy-v1`，未移植 v6。

| 选项 | 利 | 弊 |
|---|---|---|
| A 完整移植 v3 形态 | 一次到位；真实移动体验；兑现 v3 规格 | 工作量 1–2 周；与 v6 桌面工作台壳层冲突需重做外壳；回归面大（37 路由×双模式×双形态） |
| B 声明桌面优先，维持基线 | 零成本；律师核心用户确实桌面为主 | 与「便民惠民」定位矛盾——普通人问法律问题多在手机上；违背 README 对大字模式（适老化）的既有承诺 |
| C 渐进增强：先移植高价值子集（大字模式 + 44pt 触摸目标 + safe-area），BottomSheet/底部标签栏缓行 | 成本≈完整移植 1/3；**大字模式是 v2 已有、v6 丢失的能力，属回归清偿而非新增范围**；触摸目标/safe-area 基本是纯 CSS；不动现有壳层 | 非完整移动体验；底部标签栏仍缺 |

**推荐 C**。理由：普通移动用户的高频场景是「搜索/需求解析/读法条」三个轻场景，最需要的是可读性（大字）与可点性（44pt），不是完整应用壳；BottomSheet 等交互重构应等真实移动用户反馈再决定，避免为想象中的用户重做壳层。触发条件：大字模式移植完成后，若出现真实移动流量/反馈，再评估 A 的剩余部分。

## 决策项 2：jieba 引入与关键词展示策略（登记册 D4 剩余）

**现状**：确定性降级路径的 bigram 分词有跨词噪声（「老板拖欠」→「板拖」）。检索层 BM25 用同一 tokenize，**噪声对检索无害**，仅 /needs 页展示层观感问题。

| 选项 | 利 | 弊 |
|---|---|---|
| A 引入 jieba（检索+展示全换） | 分词质量本质提升 | **风险与收益错位**：换分词器须重建 BM25 索引并重跑全部金标（评测基线漂移）；jieba 版本升级可能改变切分结果，动摇「确定性可复现分词」这一 harness 价值；新增依赖破坏最小依赖现状 |
| B 仅展示层治理：/needs 优先显示规则域词（词表质量高），生成关键词降噪显示（过滤与已显示词重叠的项、限制数量、保留「由分词程序生成」诚实标注）；检索层 bigram 不动 | 零依赖零风险；解决真实观感问题；检索可复现性完整保留 | 关键词集合本身仍含噪声（只是展示收敛）；域词未覆盖的查询仍可能露出二元组 |
| C 维持现状 | 零成本 | 普通用户看到「板拖」会怀疑系统能力——伤害「可信」观感，与项目本质冲突 |

**推荐 B**。理由：项目哲学是「模型只是引擎，harness 决定可靠性」——自研确定性分词的可复现性价值高于分词先进性；噪声的实际危害仅限展示层。jieba 的再评估条件：金标评测证明检索质量受分词瓶颈限制时（目前 40 组 hit@5=0.95，无此证据）。若未来引入，须锁定版本 + 全量金标回归 + 证据链记录。

## 决策项 3：版本管理与 CI 形态（登记册 C9 剩余）

**现状**：项目**不是 git 仓库**（无版本历史、无回滚能力）；质量门为本地一键 `run_qa.cmd` 五道。

| 选项 | 利 | 弊 |
|---|---|---|
| A git init + GitHub Actions 云端 CI | 每次变更强制过门；协作/回滚/审计 | **涉及数据外发决策**（代码托管到云端，业主「非必要不决策」授权范围待确认）；私仓费用/公仓披露问题；需 CI 适配（Chrome 路径已参数化，成本低） |
| B 本地脚本即止 | 零基建；数据不出本机 | 门靠会话自觉，无强制力 |
| C **先 git 本地化（含 .gitignore 审计：排除 .venv/node_modules/app.db/证据快照大文件）+ pre-push 本地门钩子；云端 CI 待业主确认托管策略后接**（脚本就绪，迁移成本低） | git 化本身是最基础的工程债清偿；本地钩子给门以强制力；不预设云托管决策，可逆 | 两步走 |

**推荐 C**。核心理由：一个以「append-only 审计、可复核」为立身卖点的项目，自己的代码却没有版本历史——这是与项目本质最相悖的工程债。git 本地化不外发任何数据、完全可逆，不属「必要决策」；云端才需要业主拍板。

## 决策项 4：逐条 AI 解释的内容路线（登记册 B6 剩余）

**现状**：法条详情页诚实标注「AI 通用阅读指引（非本条逐条解释）」，逐条解释未接入。

| 选项 | 利 | 弊 |
|---|---|---|
| A 接 LLM gate 直接生成逐条解释 | 1,953 条全覆盖；法条详情价值大增 | **gate 验不了「解释对不对」**：引用绑定只校验条号存在，无法校验释义正确；错误解释误导公众的风险高于无解释——触碰「内容生产者责任」红线；全量生成或实时的成本/延迟 |
| B 纯人工内容工程：优先高频条文（消保法25、劳动合同法19-20、民法典188 等常问 50–100 条）人工撰写通俗解读，带编写人/审核日期字段，其余维持通用指引 | 零幻觉；可溯源到编写者；80/20 覆盖高频需求 | 生产速度慢；需法律专业输入 |
| C **双轨复用：人工解读库为主体 + LLM 仅产「草稿建议」供人工审核采用（AI 起草 → 人工核验 → 上线），未审核不展示** | 与律师函「AI 起草+律师核验签发」同构——项目已验证的化解「能力 vs 责任」矛盾的正确结构；既不虚构能力也不放弃效率 | 建设解读库 schema（author/date/reviewer/source_note）与审核流程有一次性成本 |

**推荐 C**。理由：这是把项目签名模式（双轨签发）复用到内容工程；新解读库走既有证据纪律（server/data/ + 前端禁止手写），与「宁缺毋假」完全一致。

## 决策项 5：部署时点与形态（M8-T4，业主「非必要不决策」适用）

**现状**：部署暂缓。规划方向为「第一阶段律所/法务内网 docker-compose；公网前完成备案复核」。

| 选项 | 利 | 弊 |
|---|---|---|
| A 内网 docker-compose 先行 | 合规风险最低（不面向公众则备案义务未触发）；真实反馈；工作量小 | 需内网环境与种子用户；社会价值延迟兑现 |
| B 公网直接开放原型 | 立即兑现便民价值 | **违反红线 1**（先备案/登记再对公众开放）——不可行，排除 |
| C 继续暂缓 | 零风险 | M8 其余任务（备案材料、隐私通道）失去牵引；项目停在原型 |

**推荐「条件触发的 A」**：维持暂缓，但当 **D8（PIPL 删除/导出通道）与 M8-T1 备案材料清单完成**时自动进入内网部署准备——这两项本就是上线 checklist 签核项（M8 验收 gate ③），先做完再部署零返工；同时把「要不要部署」的开放决策转化为「条件是否满足」的事实判断，最贴合非必要不决策授权。

## 决策项 6：flk 逐条比对的执行方式（M6-T1 前置）

**现状**：flk.npc.gov.cn 无开放 API；语料 1,953 条「flk 比对待办」在 UI 如实标注；pcl-2023 末条疑点待复核。

| 选项 | 利 | 弊 |
|---|---|---|
| A 人工抽查比对（如 10% 分层抽样：每部法律首末条+高频引用条+随机条）+ 字段级全量对照（条数/施行日期/机关，来自 manifest）+ 页面如实显示「抽查口径+日期」 | 合规（无爬取）；诚实（比对覆盖透明）；与风险登记册既定缓解一致 | 「逐条比对」目标缩水为「抽查+字段全量」 |
| B 对 flk 检索接口半自动逐条查询 | 名义上完成逐条 | **触碰红线 7（禁止未授权爬取）**——自动化访问公开网站仍可能违反服务条款，需法务评审且大概率不可行 |
| C 等待官方开放数据/API | 零风险 | 期限不可控，比对无限期搁置 |

**推荐 A**，并把「逐条比对完成」的验收口径修订为「抽查 ≥10% 无差异 + 字段级全量一致 + 差异清单公开」。理由：诚实降级原则同样适用于对自家完成度的表述——「如实标注抽查口径」比「宣称逐条但无法证明」更符合项目本质。
