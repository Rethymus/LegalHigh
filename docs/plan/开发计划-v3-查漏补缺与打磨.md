# LegalHigh 开发计划 v3 —— 长周期「查漏补缺与打磨」（2026-08-30）

> 定位：M5 核心链路接线完成后的**常设质量工序**。与 M6–M8（新功能/新数据）并行推进：
> M 计划回答「还缺什么能力」，本计划回答「已有能力是否真实、正确、可信、好用」。
> 项目本质 = **可信、可溯源、人机协同**的法律基础设施；打磨的目标是让每一处细节都在为这个本质作证，哪怕一处失真的数字、一个假按钮都在稀释它。

## 〇、本轮全量体检的三个透镜（方法论）

本轮（2026-08-30）对全项目做了一次「三透镜」体检，共登记 34 项发现（见 §三 登记册）。这三个透镜构成本计划的长期作业方式：

1. **代码透镜**：通读 server/web 全部源码，对照项目自己的硬约束（引用不变量、诚实降级、状态机、append-only）逐条核对。
2. **视觉透镜**：`web/scripts/qa_shots.mjs`（无头 Chrome CDP 巡检）对 29 个路由状态截图（含交互态与 390×844 窄屏），抓取 console 错误/失败请求/页面异常。**代码读不出来的问题在这里现形**：本轮最有价值的发现（窄屏破碎、纸面标题翻倍、伪 AI 摘要）全部来自视觉透镜。
3. **学科透镜**：用法学（引注规范/裁判引用顺位/条文结构）、RAG 评测学（LegalBench-RAG 口径/金标方法）、人机协同与合规（EU AI Act 日志、PIPL、生成式AI办法）的专业标准衡量现有设计，区分「原型的将就」与「产品的错误」。

**经验教训（已写进工具）**：巡检工具自身会有时序 bug（首路由截图空白=vite 冷启动；外观覆盖 localStorage 泄漏到后续路由）——视觉发现必须回到代码/复现验证后才能定级，防止「假阳性发现」驱动错误修复。

## 一、长周期运行机制（怎么持续做）

```
从登记册（§三）取未完成项（按 P0>P1>P2，同优先级按波次顺序）
```

### 1.3 波次划分（W1–W5，顺序即依赖）

**W1 数据与断言的真实性**——任何派生数字（语料规模/评测值/计数）一律实时派生或显式历史流水；演示内容必须带标注；假交互（只弹 toast 的按钮）要么实现要么降级为「规划」禁用态。*状态：本轮已完成大半（登记册 B1–B8）。*

**W2 检索与问答质量**——单一检索路径（server BM25，已落地）；多词/口语查询命中质量抽查；关键词降噪（jieba 或停用词规则，证据：needs 页出现「板拖」「个月」噪声词）；premise 前提规则扩容（现仅 4 条）；金标扩容对接 M6-T5。

**W3 合规与安全硬化**——gate2 条号校验已修复但需常测（红线路径必须有测试钉住）；audit_log 重放演练（「可重放任一文书的一生」M7 验收的前置）；CI 封装（M5-T5 后半：pytest + tsc + qa_shots + 文案 grep 四件套）；PIPL 删除/导出通道（对接 M8-T2）。

**W4 视觉与体验打磨**——**最大单项：窄屏形态决策**（C4，见 §三）：v3 自适应壳（底部标签栏/BottomSheet/安全区）留在 src-legacy-v1 未移植 v6，390×844 下应用完全破碎；对「便民惠民」定位，移动端是普通用户主场景。建议排期移植 v3 断点系统到 v6（或业主明确「律师桌面优先」后降级为自适应单栏）。其余：审计页实体 ID 可读化、LawDetail AI 解释诚实化（B6）、设置页示例控件复核、明暗双模式全路由巡检常态化。

**W5 学科深化**——引用粒度到款/项（D1）；引注含修订版本年份（D2，与 flk 比对同批）；判例负面历史检查（D3，对接 M6-T2）；LLM 开启后的 50 例抽样评测 harness（D10）；文书排版规范文档化（对接 M6-T3）。
