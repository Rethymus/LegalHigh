# LegalHigh 开发计划（2026-08-29 版）

> 前置事实底座：`docs/research/法律知识库项目深度调研报告.md`（2026-08-28，六方向调研）+ `docs/research/开源与论文调研核验-2026-08-29.md`（16 仓库 / 10 论文 / 7 部法规 1,647 条语料的本会话一手核验）。本计划只引用已核验事实。

## 〇、一句话定位

**「模型只是引擎，harness 决定可靠性」**——做一个把「检索 → 引用绑定 → 人工核验 gate → 批注留痕 → 签发交付」做成程序化工作流的便民法律服务原型，而非聊天机器人。

## 一、原型范围（本仓库 M1 可交付）

| 模块 | 交付内容 | 合规锚点 |
|---|---|---|
| **A. 引用式法律问答** | 基于 1,647 条真实法条语料的检索问答：每个回答由「命中的法条原文卡片」构成，逐条绑定 法律名+条号+版本+施行日期+来源链接；问题含错误前提时显式纠正（premise-check）；检索无命中时明确说「库内未找到依据」而不是生成 | 《生成式AI办法》第 4/9 条内容责任；引用不变量 |
| **B. 合同审查（费用/账户/责任）** | 三类条款规则引擎（审查点库对齐 CUAD 41 类范式）→ 逐条输出【风险等级｜审查点｜依据条文（带版本）｜建议改法】→ 律师批注工作流（采纳/修改/驳回）→ 全操作审计日志 → 导出带批注的审查报告 | CUAD 范式；EU AI Act 日志可追溯；PIPL 第 24 条透明度 |
| **C. 文书起草** | 律师函 / 合同 / 民事起诉状三类模板（结构化字段 + 条件分支，非自由生成）→ 实务格式排版（字体/字号/页边距/落款）→ 生成 DOCX 即可交付 → **律师函强制双轨**：AI 草稿 → 律师核验签发（未签发文档带「草稿·未核验」水印与状态机约束） | 《律师法》第 13 条非律师不得以律师名义执业；ABA 512 核验义务 |
| **D. 合规中心** | 免责声明、系统定位声明（法律信息工具，非律师/非法律意见）、模型与备案公示位、投诉通道（真实写入数据表）、数据来源与证据等级公示 | 《生成式AI办法》第 17 条公示与登记；第 14/15 条投诉处置 |

**明示不做**（红线）：诉讼代理/辩护、以律师名义执业、「包赢/100% 准确」承诺、未授权爬取裁判文书、向公众输出无核验的法律意见。

## 二、系统架构

```
┌─ web/  Vite + React 18 + TypeScript ──────────────────────────┐
│  视觉系统：Apple 风格 token 层（见 docs/design/视觉系统规范.md）    │
│  material 材质层组件：backdrop-filter 屏幕采样模糊 + 叠色 +      │
│  内高光 + hairline 边框 + 四档阴影；明暗双模式；焦点环统一        │
│  页面：问答 · 合同审查 · 文书起草 · 合规中心                       │
└──────────────┬───────────────────────────────────────────────┘
               │ REST (JSON)
┌──────────────▼─ server/  FastAPI + SQLite ────────────────────┐
│  corpus.py   法条语料加载（server/data/laws/*.json，带溯源）      │
│  qa.py       混合检索（BM25 + 条文结构加权）→ 引用卡片（无LLM依赖）│
│  review.py   条款切分 + 三类审查点规则引擎 + 依据条文绑定          │
│  annotations.py 批注状态机（待复核→采纳/修改/驳回）+ 审计日志表    │
│  drafting.py 模板引擎（律师函/合同/起诉状）+ 版本快照 + 签发状态机  │
│  docxgen.py  python-docx 排版渲染（仿宋/宋体、三号/小三、页边距）  │
│  compliance.py 免责声明/投诉工单/备案公示数据                      │
└──────────────────────────────────────────────────────────────┘
```

**检索实现决策**：原型期用 `rank_bm25`（纯 Python、可复现、零模型下载）做词法检索 + 条文结构加权（条款标题命中加权、编章上下文扩展）。这保证了**离线可运行、结果可复现、无幻觉**——回答层是「命中的法条原文」而非自由生成，天然满足引用不变量。LLM 接入层（可选）设计为独立适配器：密钥只从环境变量读取、答案必须逐句通过引用绑定校验后才允许展示（对应报告 §3.2 ALCE/RARR 范式），本仓库 P0 不默认启用。

## 三、harness 工程原则（写进代码约束）

1. **工作流而非聊天**：每个模块是固定管线，每步有程序化 gate，不设自由 Agent 循环（Anthropic《Building effective agents》：能用单次调用+检索就不上 agent）。
2. **引用不变量**：输出对象必须携带 `citations[]`，每项 = `{law_id, title, article_no, status, effective_date, source_url}`；后端校验缺引用即 500，前端无引用不渲染断言。
3. **人工核验 gate**：律师函 `draft → verified → issued` 状态机，`verified` 之前的导出文件自动加「草稿·未核验」水印；批注 `pending → adopted/amended/rejected` 单向流转。
4. **审计留痕**：annotations / 投诉 / 签发全部 append-only 落 SQLite `audit_log`（who/when/action/payload），满足 EU AI Act 高风险日志义务的工程形态。
5. **数据不编造**：语料只从 `docs/research/evidence/` 快照构建（`server/build_corpus.py`），任何新数据源必须先入证据库再进语料。

## 四、评测 harness（P0 随代码交付）

- **检索金标集** `server/tests/gold/`：人工标注的「问题 → 应命中条文」对（首批 30 组，覆盖费用/账户/责任高频问题），评测口径移植 LegalBench-RAG 的**字符级 precision/recall**（命中条文文本与金标 span 的重叠率）。
- **回归命令**：`pytest server/tests` —— 语料完整性（7 部 1,647 条、关键条文内容断言）、检索金标（precision 阈值 gate）、审查点引擎规则断言、批注状态机/审计日志断言、DOCX 生成断言。
- **看板数据**：评测结果 JSON 化，前端合规中心展示（口径与错误率公开，对应「只公开可证之事」红线）。
